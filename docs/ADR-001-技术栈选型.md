# ADR-001：智能菜谱技术栈选型

- 状态：已接受
- 日期：2026-10-10（双端方案修订）
- 决策人：产品负责人

## 背景

产品以 iOS/Android App 为主，小程序提供核心能力的轻量入口。两端共用后端、数据和领域规则；App 优先开发，小程序随后接入。核心能力包括菜谱管理、人数换算、多菜谱采购合并、下厨步骤卡和热量估算。

## 决策

采用以下技术栈：

```text
App：React Native + Expo + TypeScript + Expo Router
App 服务端状态：TanStack Query；本地跨页面交互状态：Zustand
微信小程序：Taro 4 + React + TypeScript + Zustand
后端：NestJS + TypeScript + REST API + OpenAPI/Swagger
数据层：PostgreSQL + Prisma
共享代码：pnpm workspace；共享 OpenAPI 契约与纯 TypeScript 领域 packages
图片：开发期本地文件；部署期使用对象存储
缓存：MVP 不引入 Redis；出现明确性能或异步任务需求后再加入
```

## 架构边界

- App 与小程序只通过 API 访问数据，禁止直连 PostgreSQL；
- NestJS 是人数换算、采购合并和热量计算的最终计算权威；
- `packages/contracts` 保存共享 DTO、枚举和单位定义，并以 OpenAPI 契约为准；
- `packages/recipe-engine` 与 `packages/nutrition-engine` 保存无 UI、无数据库依赖的纯业务计算；
- 两端分别实现 UI 和平台能力，共享 API、数据库、契约与领域规则，不复制后端逻辑；
- App 与微信身份通过显式账号绑定关联至同一个后端 `userId`。

## 取舍

### 为什么 App 选择 Expo + React Native

- App 是主要产品，需要 iOS/Android 原生 UI 与设备能力；
- Expo 为 React Native 项目提供导航、原生模块与构建工作流，减少从零维护移动端工程的工作；
- TypeScript 与现有 Taro/NestJS 栈一致，便于共享契约和领域代码。

### 为什么小程序继续使用 Taro + React

- 仓库已有 Taro 4 小程序工程和页面，可以延续微信端实现；
- 小程序需要按微信组件、登录、分享和审核流程单独实现与验收；
- 不以“App 页面自动转换”为目标，避免用跨端妥协限制主 App 体验。

### 为什么选择 NestJS

- 统一组织鉴权、参数校验、模块、测试、异常处理和 API 文档；
- TypeScript 与前端一致，降低共享 DTO 和团队协作成本；
- 可随业务增长拆分 recipes、shopping-lists、nutrition、community 等模块。

### 为什么选择 PostgreSQL + Prisma

- 菜谱、食材、采购清单、收藏和评论有明确关联关系与事务需求；
- Prisma 用 schema 与迁移记录数据库演进，减少前后端字段漂移。

## 后果与约束

- 必须维护三套环境：`dev`、`preview`、`production-local`；
- 所有核心业务逻辑必须通过单元测试覆盖，不允许只在页面中实现；
- App 与小程序的 UI 需分别做视觉预览和设备验收；共享领域逻辑可以复用测试，但两端交互仍需单独检查；
- 更换 React、Taro、NestJS、PostgreSQL 或 Prisma 时，需要新增 ADR、评估迁移成本，并经 preview 验收后执行。
