# 一饭清单前端架构设计（v1）

> 适用端：iOS/Android App（React Native + Expo）与微信小程序（Taro + React + TypeScript）  
> 正式应用目录：`apps/app`、`apps/miniprogram`  
> 视觉样例目录：`apps/frontend-sample`（仅用于独立预览与交互验证，不是正式小程序代码）

## 1. 架构目标

App 优先支撑“选菜 → 调人数 → 合并采购 → 下厨”的做饭准备闭环；小程序随后提供该闭环的精简入口。两端共用 API、契约和领域规则，各自实现 UI 与平台能力。

核心原则：

- 页面只负责编排和展示，不编写人数换算、合并食材或热量公式；
- 核心数据以 API 返回结果为准；客户端只维护必要的交互临时状态；
- App 使用 TanStack Query 管理服务端数据缓存，Zustand 只保存必要的跨页面交互状态；
- App 与小程序共享 `packages/contracts` 和纯 TypeScript 领域 packages，不强行复用平台 UI 组件；
- 按业务领域组织代码，避免把所有组件、请求和状态堆在 `pages/`；
- 微信平台能力集中封装，避免业务组件直接调用 `Taro.*`；
- 当前视觉样例仅做视觉参考；正式页面须使用项目组件与真实接口契约重建。

## 2. 客户端职责

| 客户端 | 定位 | 首期重点 |
| --- | --- | --- |
| App | 主产品，完整做饭管理体验 | 菜谱管理、做饭计划、采购清单、下厨、账户与偏好 |
| 微信小程序 | 轻量入口与微信内分享触达 | 浏览/分享菜谱、选菜、人数调整、采购清单、下厨核心步骤 |

App 使用 Expo Router 和 React Native 原生组件；小程序使用 Taro 页面、组件与微信平台 API。登录、分享、文件选择、通知等平台能力通过各自适配层实现。

## 3. 页面与导航

首期采用四个主 Tab，所有关键任务可在三步内到达。

```text
首页
├─ 本次做饭（选择菜谱、设置人数）
│  └─ 采购清单详情
│     └─ 下厨卡
├─ 菜谱详情
│  └─ 编辑菜谱
├─ 新建菜谱
└─ 我的

菜谱（Tab）
├─ 我的菜谱列表
├─ 菜谱详情
└─ 新建/编辑菜谱

清单（Tab）
├─ 当前采购清单
└─ 历史采购清单

我的（Tab）
├─ 个人资料
├─ 收藏（P1）
└─ 设置
```

### 首期路由表

| 路由 | 页面 | 主要职责 |
| --- | --- | --- |
| `pages/home/index` | 首页 | 展示当前做饭计划，进入选菜与生成清单 |
| `pages/recipes/index` | 菜谱库 | 搜索、筛选、选择多道菜 |
| `pages/recipes/detail` | 菜谱详情 | 查看食材、人数、步骤、热量 |
| `pages/recipes/editor` | 新建/编辑菜谱 | 创建结构化菜谱 |
| `pages/shopping/index` | 采购清单 | 查看合并项、标记已有/已购 |
| `pages/cooking/index` | 下厨卡 | 大字步骤、计时与完成状态 |
| `pages/profile/index` | 我的 | 用户与偏好入口 |

## 5. 数据、状态与接口边界

```text
App / 小程序页面与业务组件
      ↓ 调用
feature hooks
      ↓ 调用
services/*（HTTP）
      ↓ REST API
NestJS API
```

### 5.1 状态分类

| 状态 | 存放位置 | 示例 |
| --- | --- | --- |
| 服务端事实数据 | 页面 hook / 请求缓存 | 我的菜谱、采购清单、营养结果 |
| 跨页面会话状态 | Zustand store | 登录用户、当前本次做饭草稿 |
| 页面局部交互 | 组件 `useState` | 弹窗开关、加载、展开项 |
| 可恢复草稿 | 本地存储封装 | 未发布菜谱编辑草稿 |

不得在 Zustand 中复制整套菜谱列表或采购清单详情；需要刷新时应重新请求 API。

### 5.2 API 责任

| 前端动作 | 前端发送 | 后端返回/计算 |
| --- | --- | --- |
| 设置人数 | 菜谱 id、目标人数 | 已换算食材与明确提示 |
| 生成采购清单 | 菜谱 id 列表、各菜人数 | 合并、分类、来源信息 |
| 标记已有/已购 | 清单项 id、状态 | 持久化后的清单项 |
| 热量展示 | 菜谱 id、目标份数 | 总热量、每份热量、估算标识 |

前端不得自行把“勺”换算为“克”，不得为“适量”填入虚假数值。

| Token | 用途 | 建议值 |

| `radius.card` | 主卡片 | `28rpx`（按组件适配） |

视觉优先级：温暖米白底 → 深绿信息层级 → 砖橙单一主行动。首页不做信息流，不在首屏堆叠社区、统计图或功能入口。

## 7. 组件优先级

先完成以下组件，再组装页面：

1. `AppButton`：primary / secondary / text / loading / disabled；
2. `ServingStepper`：最小人数、禁用、可访问标签；
3. `RecipeListItem`：封面、名称、时长、份数与选中态；
4. `MealPlanCard`：本次做饭已选菜谱与人数；
5. `ShoppingListGroup`：分类、合并数量、已有/已购状态；
6. `CookingStepCard`：当前步骤、计时、上一步/下一步；
7. `NutritionSummary`：总热量、每份、估算说明。

## 8. 第一阶段实施顺序

1. 建立 `apps/app` Expo 工程和真实设备预览工作流，先确定首页视觉规则；
2. 在 App 完成首页、菜谱列表、菜谱详情和做饭计划的主路径；
3. 实现共享 API 契约、账号模型与核心后端接口；
4. 完成 App 做饭计划、人数选择、采购清单和下厨步骤；
5. 依据小程序范围，在 `apps/miniprogram` 接入相同 API 和用户账号；
6. 分别在 iOS/Android 模拟器或真机、微信开发者工具与微信真机检查关键流程；
7. 两端分别通过 preview 验收后再合并稳定版本。

## 9. 约束与验收

- 所有页面必须有 loading、empty 与 error 状态；
- 关键按钮必须有禁用与请求中状态，避免重复提交；
- 小程序所有交互控件应有可读标签；
- App 与小程序分别检查安全区、文字缩放、触控目标、键盘和无障碍标签；
- 页面需在微信开发者工具中检查 iPhone 与 Android 常用尺寸；
- App 页面需在 iOS 与 Android 模拟器或真机预览，不能仅以网页视觉样例验收；
- 新增 API 前先更新 `packages/contracts`，再写 service 和页面；
- 视觉样例的变更不等于正式小程序功能开发，正式接入须走 `dev → preview → production-local` 流程。
